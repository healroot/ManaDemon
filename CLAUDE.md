# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

**ManaDemon** is a World of Warcraft addon for **TBC Anniversary realms** (TBC Classic client, `## Interface: 20506`, Lua 5.1). It helps healers manage mana:

1. **Time-to-OOM (TTO)** — a live projection of when mana hits zero, shown as a one-line clock (`OOM 1:20 v  rest 2:10`; `FULL 0:45` when regen wins) in a floating widget and/or an ElvUI datatext (plus a second "current mp5" datatext). Class-generic. Rendered strings are **ASCII only** (WoW fonts have no arrow/infinity glyphs) and never contain a bare `|`.
2. **Rank dashboard** (`/md`) — per-rank mana efficiency (HPM), heal amount and HPS for the druid healing spells, with the player's current +healing, talents and TBC downranking penalties applied. **Druid-only in v1.**
3. **Advisor** — push alerts at decision moments: Innervate/mana-potion timing (fire when the deficit first exceeds the restored amount), gear-change "efficient rank shifted, rebind?" toast, and an out-of-combat drink reminder.
4. **End-of-combat summary** — one chat line per fight (net mp5, spend by spell, mana into full health, overheal %, spirit-regen-realized %, max-rank cast %, OOM moment), plus (v0.7.0) a second line counting casts on targets already above `db.simFullHp` and a third for pre-pull HoTs on full targets. Every own cast is captured with cost / target / HP-at-cast / form into a 20 s ring and labelled `utility|shift|early|overheal|ok` at the end of the fight. Last **200** fights persisted per character (`MD.cdb.fights`), zone-tagged; fights under 4 own casts are not kept.
5. **Self-calibration** (`Engine/Calibration.lua`) — every heal landed is compared with the model's prediction for it; drift is reported (`/md calibrate`, a chat line), **never fed back into the model**.
6. **Waste view** (`/md` → Waste) — overheal and wasted mana by spell / role / class / target from the combat log; **pull budget** between pulls.

Primary user is the author (Resto Druid); the TTO/advisor side is intentionally usable by any mana healer. Full design rationale and every debated decision live in **`docs/DECISIONS.md`** — read it before changing model behavior.

## Repo structure and load order

Load order is defined by `ManaDemon.toc` and matters — later files assume earlier ones populated the shared namespace:

| File | Role |
|---|---|
| `Core.lua` | Namespace, SavedVariables (`ManaDemonDB`), event dispatcher (`MD:On`), internal pub/sub (`MD:RegisterCallback`/`MD:Fire`), master 0.5s ticker (`MD:OnTick`), profile + talent scan, **the persisted profile snapshot** (`MD:WriteProfile()` → `cdb.profile`, v0.9.0: everything `RankMath:Context()` reads, so the offline tools build *this* character's kit), slash commands |
| `Data/SpellData.lua` | **Static** druid spell table (spellID → rank/level/cost/cast/heal) + known-rank index. **v0.14.3:** `SD.alias` / `SD:Resolve(id)` — some heals arrive under a different spell id from the one cast (Lifebloom's bloom is 33778, its HoT 33763), and a combat log credited 44,946 healing on one parse to a spell this table had never heard of. Aliases, never rows in `SD.spells`, which would corrupt the known-rank index. `SD:GetCost()` is **live-first** (`GetSpellPowerCost` works on this client, verified 2026-09-03) with the static table + talent modifiers (`SD:StaticCost`) as fallback and as the reference `/md verify` diffs against |
| `Engine/RegenModel.lua` | Five-second-rule state machine + regen rates straight from `GetManaRegen()` (no algebra — see DECISIONS) **plus what the client omits: Dreamstate and (v0.9.0) a measured leftover** (`RM:Unreported()` = `RM:Dreamstate()` + `RM:MeasuredMp5()`, the latter read from `cdb.mp5`, which only a clean `/md regentest` writes). **v0.9.5:** what `cdb.mp5` holds is the **leftover** — `observed - GetManaRegen - Dreamstate - party` — never the size of a tick; on a druid with Dreamstate there is normally *one* regen tick and nothing left over, and storing that tick modelled 556 mp5 for a character regenerating 279. `MeasuredMp5()` refuses any stored value larger than what the client reports and says so once; raw values stay in `RM.apiBase/apiCasting`. `RM:Effective()` weights the two rates by the measured FSR duty cycle for projections; out-of-combat observed mana-gain rate (drinking) is an EWMA over gain events |
| `Engine/SpendTracker.lua` | EWMA spend-rate estimator + its one-sigma spread (`ST:Estimate()` → rate, sigma, casts) from `UNIT_SPELLCAST_SUCCEEDED`, pull-time seed from fight history |
| `Engine/TTO.lua` | Raw state (`MD:GetManaState()`: mode oom/hold/full/warmup/ooc, tto/ttf/bound/rest, `rel`/`confident`, `cd`) computed once per tick, plus the render-only display layer (sigma-derived digit precision, value/mode latch, **confidence gate**: digits only while `sigma/net <= db.oomConfidence`, else the bound; arrow from the shown value) behind `MD:GetDisplayString`. **Never `v or 0`** — a missing value renders `OOM --` |
| `Engine/Targets.lua` | Group roster GUID → name, class, **role and roleSource** (`UnitGroupRolesAssigned` → `GetPartyAssignment` → class-implied → unknown; read, never inferred from talents). Life Tap counts per member. Fires `ROSTER_CHANGED` |
| `Engine/Overheal.lua` | Measured overheal from the combat log in six dimensions (family, spell, spell:kind, role, class, per-target session-only); wasted-mana attribution per event; persisted store decays (150-event half-life), session store does not. Latches whether the log's `amount` includes overheal (`OH:Split`) — **it does on this client (GROSS)** |
| `Engine/Calibration.lua` | Observed / predicted per spell and event kind, crits separated, no decay (a ratio is gear-invariant); resets only when the talent build changes. Reports via `/md calibrate` and a 3% drift alert. **Reads RankMath; RankMath never reads it** |
| `Engine/PullBudget.lua` | Median mana per pull in this zone from fight history → "N more, M after a drink" |
| `Engine/ManaCooldowns.lua` | Per-class big mana cooldowns (Druid live; Priest/Shaman/Paladin stubs) + carried potions, each returning the **marginal** mana it buys over `RM:Effective()`. Read by both `Engine/TTO.lua` and `UI/Advisor.lua` |
| `Engine/FightRecorder.lua` | **The full stream of one pull** (v0.7.2): damage on tracked targets, foreign heals, own casts/heals/cast-starts (with synthesized `CANCEL`), form changes, mana samples (2 s), HP snapshots (5 s), deaths — parallel arrays of numbers, indexed by the same session roster the v0.7.0 cast records use. Tracked = the party, or in a raid the player's subgroup plus main tanks. **v0.8.3:** whitelisted defensive buffs (`Data/AuraList.lua`) and every debuff on tracked targets as `K.AURA` (capped 4 per target, 10% of the budget) — recorded and drawn, **never modelled**. Gate `dur >= 20 and ownCasts >= 5`; **8 streams**, the victim is the cheapest fight that is neither pinned nor one of the 3 most recent. **v0.9.7:** each stream also carries `initial.known` — family to highest known rank id, what the player actually HAD at that pull — so a replay never draws an indicator for a spell they never trained and a coached plan never binds one. **v0.9.0:** each stream carries `initial.energize` — everything `GetManaRegen` omits for this character *at that pull* (Dreamstate + the measured mp5) — so a fight replays against what was true when it was recorded. `db.recordFights` turns it off; summaries still run |
| `Engine/RunRecorder.lua` | **A run: one dungeon, not one pull** (v0.9.1). `/md run start [name]` / `stop` / `status`. While a run is active every finished pull is handed here by `Engine/FightRecorder.lua` **instead of** the ring of 8 — the ones under the 20 s / 5 casts gate included, marked `short` — and between the pulls it records mana every 2 s, the drink buff with the mana either side of it (so the run measures its **own** drink rate; there is no preset), deaths and time dead, zone changes, Innervates and potions. **v0.13.7:** `RR:SampleHealth` also records the **party's health across the whole run, gaps included** (same 2s beat, keyed by name because a run outlives any pull's roster, stored as a fraction) -- without it a continuous run replay freezes every bar the moment a pull ends, and the gaps are where the drinking happens. Runs recorded before v0.13.7 do not have it. Two runs kept in `cdb.runs`, one pinnable; auto-stop on leaving the instance (30 s grace for a corpse run), on logout and at `db.runMaxMinutes`. Budget: `MAX_RUN_EV` for the pulls, a separate `MAX_GAP_EV` for the run's own timeline so the gaps never get squeezed out. Runs are **manual**; `Start(reason)` and `db.runAutoStart` (ships `false`) keep auto-start one `if` away. Nothing here is modelled |
| `Engine/SimPlanner.lua` | **Plans, the classifier and the card** (v0.7.4). A plan is at most 5 bound spells and 5 rules in a fixed order — "cast rank 7 here and rank 9 there" is not a strategy a human can execute. The **causality invariant is pasted at the top of the file and must stay true**: `Decide` sees only the present plus each target's trailing-5s damage. Score is a **lexicographic tuple** `(deaths, floorSeconds, manaSpent + manaOwed, -heldOn, #binds, overhealSim)` — never blended into a scalar. **v0.10.0:** `manaOwed` is the health the plan left missing, priced at the best heal-per-mana it has bound (`SP.BestHPM`) — health missing at the end is mana not yet spent, and without the term the cheapest plan that clears the danger line wins by barely healing. Nothing is earned above `db.simFullHp`, so nothing pushes a plan into overheal. `floorSeconds` counts seconds under a **measured** line: the biggest hit that target actually took in that fight, times `db.simDangerHits` — `db.simFloor`'s flat 30% is now the fallback for synthetic scenarios only. Rule 4 casts **the bound HoT whose whole heal fits the deficit** (now plus the damage arriving over the HoT's own duration), best heal-per-mana first, rather than always Rejuvenation — and **v0.11.9** it decides the second HoT on **throughput, not health**: healing already in flight (every rolling HoT's remaining ticks and Lifebloom's bloom) comes off the room before anything is chosen, and a less efficient HoT is bought only when what is in flight will not keep up with the trailing damage rate over its own duration. Wanting health *now* is rule 2's question, which is why rule 2 sits above it. The causality invariant is **tested**, not just asserted: a burst arriving at 40 s may not change a cast the plan makes before it. **v0.11.12:** the damage a rule reads is `max(trailing 5 s, the whole fight so far)` — `SM.SeenDamage`, applied events only. The trailing window alone falls to zero between swings, which made HoTs *reactive*: nothing fit until the deficit was the size of the spell. **v0.11.13:** a second, less efficient HoT is bought only when what is in flight will not cover the damage arriving **before the efficient one is castable again** — not over the worse spell's own duration, which is what stacked a Rejuvenation on a fresh Lifebloom. **v0.12.3:** every rule and the wait fill a reason record (`Because`) with the numbers that made
them fire, `SP.ReasonText` renders it and `SP.CastWhy` does the same for a recorded cast's label —
a reason is the rule's own inputs read back, never a justification, and `replaycheck` asserts field
by field that it cites nothing `Decide` was given. **v0.13.10:** `Classify` must not assume the fields of the threshold rules -- it read `plan.rollStacks`, which the solver does not have, and taking a solver plan from the replay's chooser crashed the window. `Classify` labels every real cast against the best plan in lockstep (`late`/`idle` come from a separate plan run — stated on the card). `Card` renders it; `Mark`/`Progress` close the learning loop per zone. **v0.9.3** adds the run: `SP.ChainScore` (the v0.7 tuple with **time before mana** — `deaths, floorSeconds, addedTime, drinks, manaSpent, -heldOn, #binds, overheal`), `SP.SearchRun` (the same descent over the five plan parameters **plus the two drink-policy ones**, one plan for the whole dungeon, its evaluation budget scaled down by the number of pulls), `SP.RunGates` (one validation per pull, once) and `SP.RunCard` / `SP.CoachRun`. **v0.13.8:** `CoachRun` hands the run's plan to **every pull in it** (`SP.plans[rec.id]`), which is what the replay window draws its suggested column from -- it wrote only `SP.runPlans` before, so a coached run showed an empty right column on all 36 pulls while its card said "Play one to see it". Pulls that do not replay are skipped unless `/md coachrun N force`; ones under the recording gate are never coached. `Search` is coordinate descent from 4 seeds, <= 300 evaluations, **sliced on `debugprofilestop()`** — `GetTime()` does not advance inside a frame, so slicing on it would freeze the client |
| `Engine/Intuition.lua` | **Healer intuition** (v0.13.1, `docs/SPEC-v0.13.md` §8): a prior on incoming damage learned from recordings, keyed by the two things knowable before the first hit lands — **zone and role** — with an opening rate (first 10s) and a sustained rate, per head. It exists because the solver's forecast is blind at the pull: nothing seen, so nothing expected, so it waits, while a healer who has run the place already has a Lifebloom on the tank. **The rule that makes it not cheating: a fight is never in its own prior** — `IN:Build(recs, excludeID)` takes the exclusion as a required argument and the harness asserts a fight held out of a corpus of one leaves *no* prior. One fight is an anecdote (`MIN_FIGHTS = 2`) and the weight decays to zero by 15s, so observation beats reputation as soon as there is any. **v0.13.3:** rates are **fractions of max health per second**, not raw damage, so a prior transfers between characters and content; `IN:Blur` quantises one for shipping and `IN:Load` reads it back. Two sources feed it — your own recordings (`IN:Build`, leave-one-out) and the shipped `Data/Intuition_TBC.lua`. **Ships off** (`prior` is nil unless passed): both learn the right thing but neither has been shown to *help*, and neither can be until the level 70 heal values are fixed |
| `Engine/Foresight.lua` | **Deformed foresight** (v0.13.2, `docs/SPEC-v0.13.md` §9): a blurred view of **this** fight, because a prior from other fights "can be totally irrelevant" (the author) while a blurred memory of this one cannot. Damage is bucketed at 4s, smeared into neighbouring buckets, perturbed by a deterministic hash, quantised to 6 levels, capped at 10s of sight and trusted at 0.5 — so the shape survives and the numbers do not. **Reading it is foresight and the strict causality invariant does not hold**: `plan.foresees` is true and every report says "NO - sees this fight". Every clause of the deformation is asserted in `tools/solvercheck.lua` (a one-second burst lights its bucket 6s early and reads 40% off), and it is seeded on the fight id so a replay reproduces. Ships off |
| `Engine/SimSolver.lua` | **The solver** (v0.13, `docs/SPEC-v0.13.md`): the alternative to the threshold rules. A spell is a series of **deposits** (`{dt, amount}`) built from `SpellKit`, so the schedule follows **the user's own stats** with no per-character thresholds to tune. Against them stands the demand: health missing now plus what the **causal** forecast (trailing damage, threat, an enemy cast in the air -- `docs/SPEC-v0.12.md` §2, never the real future) says will go missing. Every `(spell, target)` is scored by projecting the target twice, with and without, and taking the missing-health integral it removes per mana -- one number that carries the health gap, the overheal (a deposit above full buys no reduction) and the mana at once, and gets the timing right for free. Waiting is a priced candidate, not a fallback. The **danger line comes first**: anyone projected through it takes the cheapest cast that clears it. Rules 7 (cast), 8 (danger line) and 9 (hold) each render a sentence naming the number they decided on (`SV.ReasonText`, delegated from `SP.ReasonText`). **v0.13.5:** `sag` weights the gap integral so a missing point counts more the lower the target already is ("underheal is bad") -- implemented, tunable, and **measured inert**, so it ships at 0; and a target already under the measured danger line is at risk whatever the forecast says. `SP.STRATEGY_SET` offers three forecasts — none, an old-log prior, blurred foresight — plus rule configs, all runnable side by side by `tools/strategies.lua`. Two parameters (`minValue`, `horizon`) where the rules had five; **v0.13.4:** casting now and waiting are judged over the SAME window -- the old comparison moved the window with the delay, so under continuous damage waiting always looked better and the solver deferred almost indefinitely (26 casts on a raid fight where the healer made 82). On the author's recordings it spends **44% less** than the rules for the same deaths and floor seconds (33% was measured against v0.14.2's inflated bloom) |
| `Engine/RunTimeline.lua` | **The run's own clock** (v0.14.0, `docs/SPEC-v0.14.md`): a run is one continuous timeline, not N separate fights -- **51% of the author's Underbog run is gap**, and that is where half the mana decisions live. `RT.Build(run)` produces alternating pull and gap segments covering the whole run; `At` says which pull is running and how far in; `HpAt` / `ManaAt` answer the gaps from the v0.13.7 samples (health keyed by **name**, because a run outlives a pull's roster, and a **step function**, which is what a health bar is); `Roster` is the union of every pull's, so the window builds its rows once; `NextPull` / `PrevPull` are what the timeline bar skips by. **No frames and no client API** -- what is true at t is a pure function of the run, the same discipline `ReplayTrace` follows for a pull. A run recorded before v0.13.7 reports `hasGapHealth = false` and returns nil rather than inventing a number |
| `Engine/ReplayTrace.lua` | **The replay window's state machine** (v0.8.0): reads a run's trace (`opts.trace` on `SM:Run` — fixed-grid mana/form/HP plus `SM.TK` events: cast start/succeed/cancel, HoT apply/end, death, form, the plan's waits, each with the `Plan:Decide` rule that caused it) and answers "what is true at time t" — `Seek`, `Advance`, `Hp`, `Hot`, `Casting`, `Waiting`, `Score`. No frames, no client API: **state at t is a pure function of the trace prefix** (a seek rescans from 0 with the callback suppressed), events at t = 0 are initial state and never fire, nothing is interpolated. `SP.Replay(rec, opts)` builds both columns (recorded casts on the left, the plan Coach cached on the right) plus the recorder's real HP snapshots as ticks |
| `Engine/SimModel.lua` | **The simulation engine** (v0.7.1): one event-driven loop over a scenario, driven either by a recorded script (replay) or by a plan that decides. Binary heap for HoT ticks/expiries/decisions; recorded timelines read by cursor, never copied; per-run state from a reused pool slot. Mana leaves and the 5SR restarts when a cast **succeeds** (what the client does); regen integrated continuously. `SM.K` are the recorded event kinds — do not renumber. **v0.14.2, the HoT tick timer:** a refresh no longer restarts it — TBC's periodic effect keeps its own cadence, and re-anchoring `nextTick` made a Lifebloom rolled every 1.5s against a 1s tick fire two ticks in three. **v0.14.4 reverted the other half of v0.14.2**: Lifebloom's bloom is **one application's, flat**, not `st.bloom * st.stacks`. Pairing every bloom in the 22-parse Warcraft Logs corpus with the tick before it (the tick's size names the stack) gives the same bloom at 1, 2 and 3 stacks; the 2.1x spread that had suggested scaling was a crit (exactly 1.5x) and a +healing proc (exactly 1.30x, which also appears on Regrowth's and Rejuvenation's ticks in the same fight). `Engine/RankMath.lua` and the `endDeficit` term always had it flat. With the tick timer fixed and the harness's own calibration corrected, a raid parse reproduces **95%** of its recorded healing and no longer kills a tank nobody lost (`tools/reproduce.lua`, `docs/SPEC-v0.14.md` §4b). `ScenarioFromRecording` + `Validate` (v0.7.3) replay a recorded fight and put it through **eight gates** (mana mean/max, health per target, no tracked death, foreign share, model calibration, spend coverage), each printing its threshold's provenance. **A recording earns the right to be coached from; it is never assumed**. **v0.10.2:** `ScenarioFromRecording` splits the own casts — `script` (every one, what a replay runs) and `fixed` (the ones the healing model does not price: damage, crowd control, shapeshifts). A plan drops `script` and **keeps `fixed`**: same moment, same recorded cost, same global cooldown, same five-second-rule restart, preempting a plan cast in flight (a cancelled cast costs nothing). `spend coverage` therefore counts everything the engine *reproduces*, not only what the healing kit prices, and a healer who assists the damage dealers stops failing a gate for playing their class. **v0.9.3** `SM.ChainRun(run, kit, opts)` runs a whole run: every pull in order with mana carried across and the gaps modelled — regen at the recorded rate, a drink policy at the run's **own measured rate**, and a drink that does not fit its gap making the run longer (`addedTime`). Potions apply at their table value; an Innervate in a gap is **counted, not modelled** (its value is 400% of the spirit share, and a recording carries the total rate, not the split) |

## Conventions and constraints

- **No libraries.** Plain event frame, no Ace3. Keep it that way unless a hard need appears.
- **The model is event-driven; tickers only accumulate/render.** Never gate model updates behind UI visibility.
- **Widget visibility has a single owner** (`MD:UpdateVisibility` in `UI/Widget.lua`) with 90%/95% hysteresis. Do not call `Show()`/`Hide()` on the widget elsewhere.
- **API defensiveness:** the anniversary client's API surface is uncertain; wrap maybe-missing globals in `pcall`/existence checks (see `MD:On`, `ResolveCost`, `MD:HasBuff` for the pattern).
- **Any frame you style needs `"BackdropTemplate"`.** The backdrop mixin left the base frame in 2.5.x, so `UI.StylizeFrame` on a frame created without the template is a live error. `tools/wowstub.lua` installs the three backdrop methods only on templated frames and withholds them from its no-op fallback, so the harness fails the same way the client does.
- **`Data/SpellData.lua` values are best-effort and frozen** — any change must come from `/md verify` output or an in-game measurement, never from memory (costs were corrected that way on 2026-09-03; heal values for unlearned ranks are still `-- VERIFY`). Unverified formulas are listed in `docs/DECISIONS.md` §Open verification items.
- **Regen the client does not report** goes through `RM:Unreported()` only after an in-game `/md regentest` proves the API omits it (Dreamstate: proven). Adding a term the API already includes double counts.
- **Calibration never feeds the model.** `Engine/Calibration.lua` reports drift to a human; fixing it means changing `Data/SpellData.lua` or a formula, never scaling output by an observed ratio.
- **Lua multi-return trap:** `a and f() or b` truncates `f()` to one value. It bit twice in `UI/Summary.lua` around `Overheal:Split`; write the `if` out.
- **Constants derived from one log are settings with provenance** (`db.oomConfidence`), not hard-coded truths — the first log was a level 61 dungeon on a level 64 druid.
- enUS only for now (drink-buff names in `UI/Advisor.lua` are literal English strings).
- **Debug logging:** `MD:Debug("category", fmt, ...)` with category in regen / mana / spend / tto / heal / cast / calib / combat / chat / sim / other; it is a no-op unless enabled in the Debug Console, so it is safe on hot paths. Log state transitions and inputs, not every tick.
- **New settings UI goes through `MD.UI`** (`UI/Style.lua`) into a pane of `UI/Options_General.lua`, not into the dashboard.

## Verifying changes

There is no build system. A change is "verified" when:
1. `luac -p <file>` passes (any Lua ≥5.1 syntax check is fine),
2. the file is listed in `ManaDemon.toc` in a position consistent with what it reads from `MD`, and
3. **for anything the engine or the recorder touches, both harnesses still pass**:
   `tools/run.sh tools/simcheck.lua` (ten self-tests over `Engine/SimModel.lua` plus the BF-1
   fixture replay), `tools/run.sh tools/reccheck.lua` (a scripted pull end to end, 38
   assertions), `tools/run.sh tools/replaycheck.lua` (the trace and the replay state machine, 31
   assertions), `tools/run.sh tools/replayui.lua` (the replay window painted under the stub, 50
   assertions — the only UI file with an offline test) and, for the regen diagnostics,
   `tools/run.sh tools/regencheck.lua`. They run the real files under a stub client, so they catch ordering and
   arithmetic bugs a syntax check cannot — between them they have already found the engine's
   sample-ordering bug and a roster-index ordering bug in the recorder. This is the closest
   thing the repo has to a test suite; keep `tools/harness.lua`'s file list in step with the
   `.toc`.

Functional testing happens in-game: `/md verify` first (data + input snapshot), `/md fsrtest` for the five-second-rule anchor, then play. The neighboring `../ElvUI*` folders (if present in the parent AddOns checkout) are read-only reference code for datatext patterns.
